1. Blockers — Must Change

These items must be resolved before the collection can integrate with the dashboard or ship as an EE.

1.1 Blocker Missing meta/compliance-profile.yml

The dashboard uses this single file for profile identity, display configuration, platform guards, and certification metadata. Without it, the profile cannot be registered or discovered.

Must include: slug, name, framework, version, platform, scanner, remediation_playbook, remediate_jt_name, certification block, platform_spec with os_family: ["Windows"], and full display config (gauge_label, gauge_unit, severity_map, columns).

Reference: any RHEL profile at profiles/rhel9-stig/.../meta/compliance-profile.yml.

1.2 Blocker Missing install.yml and uninstall.yml

No install playbook exists. This is how profiles register their assessment and remediation Job Templates on Controller. Must create JTs with correct extra_vars embedding profile metadata (slug, remediate_jt_name, remediation_playbook), ask_variables_on_launch: true, ask_inventory_on_launch: true.

Reference: profiles/rhel9-stig/install.yml and profiles/supply-chain/install.yml.

1.3 Blocker Results push uses wrong API pattern

push_results.yml sends the full findings array as body_format: json to a non-existent endpoint. This will OOM on large scans and doesn't match the dashboard's ingest API.

Required pattern (ADR-033/034): Normalizer writes NDJSON files via compose_post_body (preamble + one finding per line). Playbook POSTs each file using uri with src: parameter (streams from disk). Content-Type: application/x-ndjson. Endpoint: /api/compliance/findings/ingest. Must loop per-host (ADR-030).

1.4 Blocker PowerSTIG scan modifies target hosts

The normalize_powerstig role runs Start-DscConfiguration -Force which applies the DSC configuration before testing it. A scan/audit operation must never modify the target. Fix: use Test-DscConfiguration -Path ... -Detailed directly without Start-DscConfiguration.

1.5 Blocker Zero unit tests

Our RHEL profiles have 127 collection tests (19 per XCCDF profile + 44 CycloneDX + 60 cross-profile structure). This collection has none.

Minimum: test_compliance_evaluate.py (all check types, operators, severity mapping, error handling), test_cff_filters.py (all 3 filters, status/severity mapping, dual output), test_crosswalk_filters.py (control mapping, summary computation). Target: 40+ tests.

1.6 Blocker Missing proper EE definition for delivery

No ee/execution-environment.yml at the profile root level. The EE definitions under extensions/patterns/ reference ee-minimal-rhel9 with Python deps but don't follow the ansible-builder v3 build pattern our CI uses.

Must include: base image, galaxy deps (infra.windows_ops, ansible.windows, community.windows), Python deps (pywinrm, requests-credssp, requests-ntlm), verification steps in append_final.

1.7 Blocker License mismatch

galaxy.yml declares license_file: LICENSE (Apache-2.0) but COPYING contains GPL-3.0. The upstream infra.windows_ops dependency is GPL-3.0. A wrapper collection with GPL deps should be GPL-3.0.

2. Quality — Should Change

Important for correctness and maintainability but not strict blockers.

2.1 Quality Duplicate evaluation logic

Rule evaluation is implemented twice: compliance_evaluate.py (module, 267 lines) and evaluate_rule() in cff_filters.py (100+ lines). Both implement the same operators, check types, and error handling with slight differences. Keep the module, remove the filter function.

2.2 Quality Rule schema duplication

Each rule has redundant fields: path duplicates check.params.key, expected duplicates check.params.value, check_type duplicates check.type. Pick one schema — recommend the nested check structure.

2.3 Quality Only 10 of 248+ rules shipped

The infra.windows_ops collection has 248 automated rules for Windows Server 2022 V2R7. Crosswalk profiles reference V-IDs that don't exist in the rules file. Generate the full rules YAML from upstream control matrices (similar to our extract_rule_metadata.py).

2.4 Quality Terminology: "Backstage" references

Replace "Backstage" with "Ansible Portal" in portal/catalog-info.yml, push_results.yml, and any comments. Replace "compliance cartridge" with "compliance profile".

2.6 Quality Missing aap_impact classification

Rules don't have aap_impact or aap_impact_reason fields. The dashboard uses these to show remediation warnings. For Windows, breaks-connectivity would apply to rules affecting WinRM (firewall, TLS, service accounts).

Don't split the collection. The shared infrastructure (CFF filters, compliance_gather, crosswalk engine) would be duplicated. Instead, register each framework as a separate compliance profile in the dashboard:

4. Legal Analysis: DISA SCC Distribution

The dual-nature problem

DISA Security Compliance Checker (SCC) is public domain under 17 USC § 105 (government work). However, NIWC Atlantic signed an exclusive commercial licensing deal with Ignyte Platform for binary redistribution rights. The installer has an undisclosed EULA, creating legal ambiguity.

Chocolatey precedent

The Chocolatey community package for SCC (scap-compliance-checker) downloads the installer at install time from dl.dod.cyber.mil rather than embedding the binary. This is the industry standard approach for avoiding redistribution concerns.

Risk assessment

Distribution MethodLegal RiskReasoning
Embed SCC in EE imageHIGHPotential breach of Ignyte exclusive license, ambiguous EULA terms, no vendor precedent
Download at scan timeLOWDirect download from DoD authoritative source, explicit Distribution Statement A, matches Chocolatey pattern
Cache after downloadLOWLocal cache for air-gapped scenarios, not redistribution

Architecture: ephemeral download with cache fallback (ADR-038 §2)

Scan time (Play 0 — localhost/EE):
  1. Try download SCC from dl.dod.cyber.mil → cache to /tmp/compliance-scc/
  2. If download fails AND cached copy exists → warn + continue with cached
  3. If download fails AND no cache → fail with clear error

Play 1 (targets via WinRM):
  4. win_copy SCC + SCAP benchmark from EE to target
  5. Run cscc -u (unattended scan)
  6. fetch XCCDF results back to EE
  7. Remove SCC + benchmark from target

Play 2 (localhost/EE):
  8. normalize_xccdf per host (REUSE existing _shared/normalize_common.py)
  9. Compose NDJSON + POST to API (ADR-033/034)

Key advantages

  • SCC outputs standard XCCDF XML — same format as OpenSCAP. Our existing normalize_common.py parses it unchanged.
  • SCAP benchmark content IS freely redistributable (public domain, hosted on GitHub). This can be pre-baked into the EE.
  • Export control: not an issue. SCC carries Distribution Statement A, which explicitly permits distribution to foreign nationals and governments.

5. Crosswalk Architecture

HIPAA and PCI-DSS are not profiles

They are regulatory crosswalk views computed from existing STIG or CIS scan findings. They do NOT run separate scans or have separate normalizers.

Implementation: dynamic tab widgets (extends ADR-027)

Each compliance profile declares crosswalk tabs in its compliance-profile.yml display config. The tabs are dynamically installed when the profile is connected and removed when disconnected — no separate install step.

display:
  tabs:
    - key: "hipaa"
      label: "HIPAA"
      icon: "policy"
      crosswalk_framework: "hipaa"
      source_framework: "STIG"
      layout:
        - widget: crosswalk_summary
          title: "HIPAA Security Rule — Technical Safeguards"
          show_gaps: true
        - widget: crosswalk_controls_table
          title: "Control Status"

Data flow: client-side join

The crosswalk computation happens in the dashboard frontend. It's a join between:

  1. Scan findings (already in the DB from STIG/CIS scans)
  2. Control mapping definition (stored in the profile's displayConfig)

No second scan. No backend API changes. No separate normalizer.

New widget types required

Widget TypePurposeEffort
crosswalk_summaryShows overall control coverage (pass/fail/partial/gap/unmapped counts)1–2 days
crosswalk_controls_tablePer-control detail with mapped rule statuses1–2 days

Crosswalk definition data

Steve's hipaa.yml and pci_dss_v4.yml ship inside security.compliance_windows and are referenced by the profile's compliance-profile.yml. The install.yml reads it and includes it in the profile registration payload.

This extends ADR-027 (Dynamic Tab System) with two new Tier 1 widget types.

8. What's Good (Keep As-Is)

  • CFF filter architecture — Three distinct filters (to_cff_stig, to_cff_cis, to_cff_powerstig) with dual camelCase/snake_case output. Right pattern for multi-scanner support.
  • Crosswalk engine — HIPAA and PCI-DSS crosswalks with pass/fail/partial/gap/unmapped per control. Bonus value none of our RHEL profiles have. Clean, reusable filters.
  • Track A pre-assessment — compliance_gather with Gather-ComplianceData.ps1 collecting registry, secpol, auditpol, and services in a single WinRM round-trip. The fast-scan model our assessment doc recommended.
  • Argument specs on all 6 roles — Typed parameters in meta/argument_specs.yml. Our RHEL profiles don't have these yet.
  • PowerShell script quality — Gather-ComplianceData.ps1 is well-structured with error handling, temp file cleanup, JSON output. Single-round-trip design minimizes WinRM overhead.
  • Multi-scanner design — Supporting both infra.windows_ops (Ansible-native) and PowerSTIG (DSC-native) via compliance_scanner variable. Matches Tier 1/Tier 2 architecture (ADR-001).
  • Pattern metadata — extensions/patterns/ follows SDP-0005 structure with source_collection, wrapper_collection, normalizer_role, scanner_options.
