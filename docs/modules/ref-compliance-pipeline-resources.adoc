== Assessment architecture

The assessment uses a **single job template** (`compliance-run-oscap`) running `run_oscap.yml` with two plays in one JT. No workflow is needed for Tier 1 (OpenSCAP) assessment.

[cols="1,2,2", options="header"]
|===
|Play
|Runs On
|Purpose

|Play 1
|Target hosts (via SSH)
|Install oscap, copy datastream from EE, run `oscap xccdf eval`, fetch XCCDF XML back, cleanup

|Play 2
|localhost (same container)
|Normalize XCCDF XML to CFF JSON via `normalize_xccdf` module (per-host processing)
|===

Both plays run in the same container, so Play 1's fetched files are available to Play 2. A multi-node workflow would fail because each workflow node runs in a separate container and fetched files are not shared between nodes.

Remediation is launched as a **separate, standalone job template** with `job_tags` for selective rule execution. It is not part of the assessment.

== Scanner certification levels

Each compliance profile declares a certification status that indicates whether its scan results are formally recognized by the compliance framework authority. The compliance plugin displays this as a badge on scan results.

[cols="1,2,2", options="header"]
|===
|Status
|Meaning
|Example

|`certified`
|The scanner is validated by the framework authority. Results are accepted for formal compliance audits.
|OpenSCAP + DISA STIG (OpenSCAP has NIST SCAP 1.2 validation; SSG content is produced in collaboration with DISA FSO)

|`conformant`
|The scanner uses official benchmark content but is not the authority-certified tool. Results are technically accurate but may not be accepted for formal audits.
|OpenSCAP + CIS Benchmark (CIS-CAT Pro is the CIS-certified scanner, not OpenSCAP)

|`uncertified`
|Custom scanner or homegrown checks with no formal validation.
|Ansible facts gathering with custom rules
|===

The certification status is declared in the compliance profile's `meta/compliance-profile.yml` and emitted in the Common Findings Format (CFF) JSON output by the normalizer module.

== API endpoints

The Compliance Dashboard plugin communicates with {ControllerName} through the platform gateway. All endpoints use the `/api/controller/v2/` base path.

[cols="2,1,3", options="header"]
|===
|Endpoint
|Method
|Purpose

|`/api/controller/v2/job_templates/`
|GET
|List job templates available for compliance scans and remediation

|`/api/controller/v2/job_templates/<id>/launch/`
|POST
|Launch an assessment scan or remediation job with inventory, extra variables, limit, and job tags

|`/api/controller/v2/jobs/<id>/`
|GET
|Check the status of a running or completed job

|`/api/compliance/findings/ingest`
|POST
|Primary findings delivery channel. The normalize play POSTs CFF JSON findings directly to the plugin API using a per-scan ingest token (Direct POST, see ADR-007 and ADR-010).

|`/api/controller/v2/jobs/<id>/job_events/`
|GET
|Retrieve job events for status monitoring and fallback findings parsing (if Direct POST is not configured)

|`/api/controller/v2/jobs/<id>/stdout/`
|GET
|Retrieve raw job output for log display

|`/api/controller/v2/inventories/`
|GET
|List inventories available for scan targeting

|`/api/controller/v2/execution_environments/`
|GET
|List execution environments for compliance profile registration
|===
