= About the Compliance Dashboard

[role="_abstract"]

The Compliance Dashboard provides scanner orchestration for {PlatformNameShort}, enabling organizations to assess, report on, and remediate the compliance posture of their managed infrastructure. The compliance plugin integrates with {ControllerName} to execute scanning and remediation workflows, and surfaces results through a self-service interface in the Ansible Automation Portal.

== Scanner model

The Compliance Dashboard uses a three-tier scanner model that accommodates different levels of scanner integration and organizational requirements:

Tier 1 (Fully shippable)::
Scanners that Red Hat can package and distribute as part of the compliance content. These scanners run entirely within an {ExecEnvShort} and require no external dependencies beyond what is included in the container image.
+
Example: OpenSCAP with SCAP Security Guide content for RHEL DISA STIG assessments.

Tier 2 (Bring Your Own Scanner)::
Scanners where the customer provides their own licensed scanner software. The compliance pipeline provides the orchestration framework (job templates, workflow templates, and result parsing), but the scanner binary and license are supplied by the customer.
+
Example: A commercial vulnerability scanner that requires a per-host license.

Tier 3 (Hybrid)::
Scanners that combine Red Hat-shipped components with customer-provided configuration or content. The compliance pipeline ships the orchestration and base scanner, while the customer supplies custom policies, benchmarks, or rule overlays.
+
Example: OpenSCAP with a customer-authored XCCDF tailoring file.

== Scanning tracks

The Compliance Dashboard supports two scanning tracks that serve different purposes in the compliance lifecycle. The current implementation uses Track B (OpenSCAP audit-grade scanning). Track A is planned for a future release.

Track A (Pre-assessment) -- _planned_::
Lightweight scans that provide a rapid compliance posture check. Pre-assessment scans are designed to run frequently (daily or on-demand) with minimal impact on target systems. Results are informational and help teams identify drift before a formal audit. This track is not yet implemented.

Track B (Audit-grade) -- _current implementation_::
Full-depth scans that produce evidence suitable for auditor review. Audit-grade scans generate detailed XCCDF results, HTML reports, and per-rule evidence artifacts. These scans are typically run on a scheduled basis aligned with audit cycles. The current implementation uses OpenSCAP with SCAP Security Guide content.

== Integration with {PlatformNameShort}

The Compliance Dashboard integrates with the following {PlatformNameShort} components:

{ControllerName}::
Job templates orchestrate the scan and remediation cycle. For Tier 1 scanners (OpenSCAP), assessment uses a single job template with two plays. Each compliance profile maps to a set of job templates that run within a dedicated organization. Job templates support launch-time prompts for inventory scope, rule selections, and remediation parameters.

Execution environments::
Compliance scanners and their dependencies are packaged as {ExecEnvShort}s. This ensures that scanner binaries (such as `openscap-scanner`), SCAP content (such as `scap-security-guide`), and required Python libraries are available on execution nodes without modifying the node operating system.

Platform gateway::
The compliance plugin communicates with {ControllerName} through the platform gateway API (`/api/controller/v2/`). Authentication uses per-user OAuth2 tokens or service account tokens, and all API calls are subject to {ControllerName} RBAC.

== Compliance profiles

A compliance profile is a registered standard that maps a compliance framework (such as DISA STIG or CIS Benchmark) to the {PlatformNameShort} resources required to assess it. Each profile specifies:

* The assessment job template that orchestrates the scan
* The {ExecEnvShort} containing the scanner and content
* The inventory scope (which hosts to assess)
* The compliance framework version and rule set

Each profile also carries a canonical rule count from the compliance standard metadata (for example, 489 rules for DISA STIG RHEL 9). This count reflects the total rules defined in the standard and is stable regardless of which inventory was last scanned or how many hosts returned results.

Profiles are registered in the compliance plugin settings and can be shared across teams within an organization.

== Authoritative scan

When you launch a remediation, the system must determine which hosts have failing rules and what evidence supports the remediation scope. The compliance plugin automatically identifies the _authoritative scan_ for each (profile, inventory) pair: the latest completed assessment scan that used that compliance profile against that inventory.

The authoritative scan serves two purposes:

* It determines which hosts need remediation and which rules are failing on each host.
* It is recorded as the _informing scan_ on the remediation execution record, establishing a clear audit trail from assessment evidence to remediation action.

If no completed assessment scan exists for the selected profile and inventory combination, the plugin blocks the remediation launch and offers to run a scan first.

== Finding lifecycle states

Each finding tracks its lifecycle state across consecutive scans for the same compliance profile and inventory:

New:: A rule that failed for the first time. Not present in the previous scan for this profile and inventory combination.
Active:: A rule that continues to fail across consecutive scans. The finding was already present in the previous scan.
Fixed:: A previously failing rule that now passes. Indicates successful remediation.
Resurfaced:: A rule that was previously fixed but has regressed to failing. Indicates a compliance regression.

== Plugin architecture

The Compliance Dashboard plugin consists of three packages:

* *Frontend plugin* (`@aap-compliance/plugin`): Provides the user interface with six tabs -- Overview, New Scan, Results, Remediations, Inventories, and Settings. Key features include:
** *CSV and JSON export* -- Export findings from any scan result for auditors or integration with external tools.
** *Verification comparison view* -- After remediation, compare before-and-after compliance scores with side-by-side gauges showing pass-rate improvement.
** *Dual view modes* -- View findings organized by status (pass/fail) or by category (Access Control, Audit, etc.) for flexible analysis.
** *Cross-profile filtering* -- When reusing an existing remediation from scan results, the Remediations tab filters to show only profiles that match the current compliance standard.
** *Inventory-aware remediation launch* -- When launching a saved remediation, you select a target inventory and the system validates that a completed assessment scan exists before allowing the launch.
** *Insights pattern* -- Remediation profiles auto-save as you configure them, with inline naming that removes manual save steps.
** *Data retention settings* -- Configure how long scan findings are retained, with manual cleanup support for immediate space reclamation.
* *Backend plugin* (`@aap-compliance/backend`): REST API that communicates with {ControllerName}, manages scan state, and stores remediation profiles in a database. The backend implements automatic data retention cleanup on startup and exposes settings and cleanup endpoints for administrative control.
* *Common package* (`@aap-compliance/common`): Shared TypeScript types for profiles, findings, and API contracts.
