= Configuring the Compliance Dashboard

[role="_abstract"]

Configure the Compliance Dashboard on your {PlatformNameShort} instance to enable automated compliance scanning, remediation, and verification of managed hosts. This procedure creates the required {ControllerName} resources and connects the compliance plugin to your {PlatformNameShort} deployment.

.Prerequisites

* {PlatformNameShort} {PlatformVers} or later is deployed and accessible.
* The Ansible Automation Portal is deployed with the compliance plugin installed.
* You have administrator access to {ControllerName}.
* Target hosts are running RHEL 9 and are registered in an inventory.
* `ansible-builder` is installed if you need to build a custom {ExecEnvShort}.
* `podman` or `docker` is available for building container images.

.Procedure

. Create a dedicated organization in {ControllerName} for compliance resources.
+
Log in to {ControllerName} and navigate to *Organizations* > *Add*.
+
Set the following values:
+
[cols="1,2", options="header"]
|===
|Field
|Value

|Name
|`compliance-prototype`

|Description
|Compliance pipeline resources -- isolated from production resources
|===
+
Click *Save*.

. Create a project that points to the compliance content repository.
+
Navigate to *Projects* > *Add* and set the following values:
+
[cols="1,2", options="header"]
|===
|Field
|Value

|Name
|`compliance-content`

|Organization
|`compliance-prototype`

|Source Control Type
|Git

|Source Control URL
|`https://github.com/cross-logic/aap-compliance-pipelines.git`

|Source Control Branch
|`main`

|Update Revision on Launch
|Enabled
|===
+
Click *Save*, then click *Sync* to pull the project content.

. Register or build the compliance {ExecEnvShort}.
+
The compliance {ExecEnvShort} packages OpenSCAP, SCAP Security Guide, and required Ansible collections into a container image.
+
To build the {ExecEnvShort} from source, run the build script:
+
[source,bash]
----
cd aap-compliance-pipelines
./scripts/build-ee.sh compliance-stig-rhel9:latest
----
+
To push the image to a container registry accessible by your execution nodes:
+
[source,bash]
----
podman push compliance-stig-rhel9:latest <your-registry>/compliance-stig-rhel9:latest
----
+
Register the {ExecEnvShort} in {ControllerName} by navigating to *Execution Environments* > *Add* and setting the following values:
+
[cols="1,2", options="header"]
|===
|Field
|Value

|Name
|`Compliance STIG RHEL 9`

|Image
|`<your-registry>/compliance-stig-rhel9:latest`

|Organization
|`compliance-prototype`
|===

. Create an inventory for the target hosts.
+
Navigate to *Inventories* > *Add* > *Add Inventory* and set the following values:
+
[cols="1,2", options="header"]
|===
|Field
|Value

|Name
|`compliance-rhel9-inventory`

|Organization
|`compliance-prototype`
|===
+
After saving, navigate to the *Hosts* tab and add each RHEL 9 host that you want to scan.

. Create the assessment job template.
+
The assessment architecture uses a *single job template* (`compliance-run-oscap`) running `run_oscap.yml`, which contains two plays: Play 1 scans targets via SSH, Play 2 normalizes results on localhost. Both plays run in the same container, so no workflow is needed for Tier 1 (OpenSCAP) assessment.
+
[NOTE]
====
AAP workflow nodes run in separate containers. The scan play fetches XCCDF result files from targets to the execution node, but a second workflow node cannot access those files. Combining scan and normalize into one JT (two plays) solves this.
====
+
Navigate to *Templates* > *Add* > *Add Job Template* and set the following values:
+
[cols="1,2", options="header"]
|===
|Field
|Value

|Name
|`compliance-run-oscap`

|Job Type
|Run

|Inventory
|`compliance-rhel9-inventory`

|Project
|`compliance-content`

|Playbook
|`profiles/rhel9-stig/ansible_collections/security/compliance_rhel9_stig/playbooks/run_oscap.yml`

|Execution Environment
|`Compliance STIG RHEL 9`

|Credentials
|Machine credential with SSH + become access

|Prompt on Launch: Inventory
|Enabled

|Prompt on Launch: Limit
|Enabled

|Prompt on Launch: Variables
|Enabled

|Use Fact Storage
|Enabled
|===
+
[IMPORTANT]
====
*Use Fact Storage* must be enabled on the assessment job template. The scan playbook gathers host facts (`ansible_os_family`, `ansible_distribution_major_version`) during each scan, and Controller persists these facts only when this setting is enabled. The compliance plugin uses these cached facts for platform validation -- checking that inventory hosts match the compliance profile's platform requirements before launching scans.
====
+
Verification scans use this same job template -- a verification scan is simply another assessment run after remediation has been applied. There is no separate verification template.
+
To add CIS Benchmark profiles alongside STIG, create additional assessment job templates using the same pattern. Set the *Name* to `compliance-scan-cis-l1-rhel9` (for CIS Level 1) or `compliance-scan-cis-l2-rhel9` (for CIS Level 2), and set the *Playbook* to the corresponding profile path under `profiles/rhel9-cis-l1/` or `profiles/rhel9-cis-l2/`. All three profiles share the same {ExecEnvShort} because `scap-security-guide` ships all XCCDF datastreams. Register each profile separately in the compliance plugin *Settings* tab.
+
[NOTE]
====
*Direct POST configuration*: The assessment job template receives three extra variables from the plugin at launch time: `scan_id`, `backstage_api_url`, and `ingest_token`. The normalize play (Play 2) uses these to POST findings directly to the plugin's `/findings/ingest` endpoint, bypassing job event parsing for faster and more reliable delivery (see ADR-007 and ADR-010). The `Prompt on Launch: Variables` setting must be enabled on the job template for these values to be accepted. If `backstage_api_url` is not set, findings fall back to Controller job event parsing.
====

. Create a remediation job template.
+
Remediation is launched as a *separate, standalone job template* -- not part of the assessment. The gap between assess and remediate is where intelligence lives: human review, EDA policy evaluation, or future AI-driven decisions.
+
Navigate to *Templates* > *Add* > *Add Job Template* and set the following values:
+
[cols="1,2", options="header"]
|===
|Field
|Value

|Name
|`compliance-remediate`

|Job Type
|Run

|Inventory
|`compliance-rhel9-inventory`

|Project
|`compliance-content`

|Playbook
|`profiles/rhel9-stig/ansible_collections/security/compliance_rhel9_stig/playbooks/remediate.yml`

|Execution Environment
|`Compliance STIG RHEL 9`

|Credentials
|Machine credential with SSH + become access

|Prompt on Launch: Inventory
|Enabled

|Prompt on Launch: Job Tags
|Enabled

|Prompt on Launch: Limit
|Enabled

|Prompt on Launch: Variables
|Enabled

|Enable Privilege Escalation
|Enabled
|===
+
The compliance plugin passes selected rule IDs as `job_tags` and parameter overrides as `extra_vars` when launching remediation.

. Create an API token for the compliance plugin.
+
Navigate to your user profile in {ControllerName} and select *Tokens* > *Add*.
+
Set the *Scope* to *Write* and note the generated token value. The compliance plugin uses this token to launch job templates and retrieve results.
+
[IMPORTANT]
====
Store the API token securely. It provides write access to {ControllerName} resources within the scope of your user permissions.
====

. Configure the compliance plugin in the Ansible Automation Portal.
+
Add the compliance plugin settings to the portal's `app-config.yaml`:
+
[source,yaml]
----
compliance:
  dataSource: live
  retentionDays: 90
  authMode: production

ansible:
  rhaap:
    baseUrl: https://<your-aap-gateway-hostname>
    checkSSL: true
    token: ${AAP_API_TOKEN}
----

. Configure RBAC.
+
Enable RBAC enforcement by adding the compliance plugin to the permission evaluation list.
+
In your `app-config.yaml`, add `compliance` to the RBAC plugins list:
+
[source,yaml]
----
compliance:
  authMode: ${COMPLIANCE_AUTH_MODE:-development}

permission:
  enabled: true
  rbac:
    pluginsWithPermission:
      - catalog
      - scaffolder
      - permission
      - compliance
----
+
The compliance plugin uses the same two-tier permission model as the self-service plugin. Users in the `aap-admins` group (AAP superusers) can perform all actions. All other authenticated users have read-only access.
+
Additionally, the plugin passes each user's AAP OAuth2 token to {ControllerName} API calls, so AAP's native RBAC controls which inventories, job templates, and credentials the user can access.

. Restart the Ansible Automation Portal to load the compliance plugin with the updated configuration.

.Verification

* Open the Ansible Automation Portal in a web browser and navigate to the *Compliance* section in the sidebar.
* Go to the *Settings* tab and register the RHEL 9 STIG compliance profile by selecting the assessment job template and {ExecEnvShort} you created. To modify an existing profile, click the edit icon (pencil) next to the profile row.
+
[NOTE]
====
When you select a scan job template in the *Settings* form, the plugin fetches the JT's default `extra_vars` from {ControllerName}. If the JT was provisioned using the profile's `install.yml` playbook, its extra_vars contain profile metadata (`profile_name`, `framework`, `certification_status`, `certification_authority`, and `platform_spec`), and the form fields auto-populate with these values. All fields remain editable. If the JT has no extra_vars (for example, a manually created JT), you must fill in the fields manually. Each compliance profile collection includes a `meta/compliance-profile.yml` file that documents these values.
====
* Go to the *New Scan* tab and launch a test scan against a single host.
* Verify that the scan appears in the *Results* tab and that findings are displayed after the job completes.
