Key Deployment Inconsistencies

deployment-guide.md says auth is "unauthenticated" — this is wrong

The deployment guide states: "All API routes are marked unauthenticated in the backend. This is the default for local development with guest auth."

Since the security hardening session (Jun 29), production auth is the default. The dev config explicitly sets development mode. This doc is actively misleading for anyone deploying to production.

deployment-guide.md doesn't reference standalone-deployment.md
The standalone deployment guide was created Jul 6, but the main deployment guide has no link to it and no mention that a simpler single-server option exists. Someone reading deployment-guide.md would think Portal/RHDH is the only deployment path.
"Managing compliance" Google Doc doesn't mention standalone deployment
The Red Hat product doc describes only the Portal deployment model. It should at minimum note that a standalone mode exists for evaluation, with a link to the guide.

Proposed Dual-Format Template

Every Markdown document should have a YAML frontmatter preamble for machine readability, followed by content formatted per Red Hat documentation conventions. Here are templates by document type:

Template A: Guides and Reference Docs

--- title: "Standalone Deployment Guide" description: "Deploy the AAP Compliance Dashboard as a standalone application for demos and testing" type: guide # guide | reference | concept | procedure audience: [operator, developer] # developer | operator | architect | auditor product: "AAP Compliance Dashboard" product_version: "2.6" status: current # current | draft | deprecated last_verified: 2026-07-06 prerequisites: - Node.js 20+ - Corepack enabled related: - deployment-guide.md - architecture-diagram.md --- # Standalone Deployment Guide [Red Hat documentation body follows — structured with Prerequisites, Procedure, Verification, Troubleshooting sections per RH conventions]

Template B: Architecture Decision Records

--- title: "ADR-037: OCI Artifact Push Pattern" description: "How compliance profiles push SBOM artifacts to PAH via oras" type: adr status: accepted # proposed | accepted | deprecated | superseded date: 2026-07-01 supersedes: null superseded_by: null decision_drivers: - OCI artifact storage - PAH registry integration related_adrs: [ADR-031, ADR-032] --- # ADR-037: OCI Artifact Push Pattern ## Status Accepted (2026-07-01) ## Context [body follows standard ADR format: Context, Decision, Consequences]

Template C: Feature Specs

--- title: "Supply Chain Vulnerability Scanning" description: "Syft/Grype SBOM pipeline for container and host vulnerability detection" type: feature-spec status: implemented # proposed | in-progress | implemented | deferred priority: P2a implements_adrs: [ADR-029, ADR-033, ADR-034] last_verified: 2026-07-01 --- # Feature: Supply Chain Vulnerability Scanning [body follows]
Why this matters: With 67 documentation files and growing, AI models (Claude, internal tools, future doc search) cannot efficiently triage which document answers a question without reading all of them. YAML frontmatter enables:
  • Instant document classification and filtering
  • Automated staleness detection (last_verified vs today)
  • Dependency graphing (related, implements_adrs)
  • Audience-aware retrieval (show operators the deployment guide, not ADRs)
